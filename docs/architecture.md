## 1. 系统概览

Snack 是一个前后端分离的 Web 贪吃蛇游戏，支持分数上传与排行榜。

**核心组成：**

- 前端：浏览器中运行的游戏界面与交互逻辑
- 后端：提供 REST API，负责分数存储与排行榜查询
- 数据库：持久化玩家分数数据

**定位：** 练习企业级全栈开发流程的项目，不追求功能复杂度，追求工程规范完整。

---

## 2. 整体架构

采用经典的**前后端分离**三层架构：

```text
┌─────────────────┐
│   浏览器（用户）  │
└────────┬────────┘
         │ HTTP / REST
         ▼
┌─────────────────┐
│  前端 Vue3 SPA   │
│  （静态资源）     │
└────────┬────────┘
         │ HTTP / JSON
         ▼
┌─────────────────┐
│ 后端 Spring Boot │
│  Controller      │
│  Service         │
│  Repository      │
└────────┬────────┘
         │ JDBC
         ▼
┌─────────────────┐
│      MySQL       │
└─────────────────┘
```

**分层职责：**

| 层 | 职责 |
|---|---|
| 前端 SPA | 渲染界面、处理交互、游戏逻辑 |
| Controller | 接收 HTTP 请求、参数校验、返回响应 |
| Service | 业务逻辑 |
| Repository | 数据访问（JPA / MyBatis） |
| MySQL | 数据持久化 |

## 3. 技术选型决策

### 3.1 前端：Vue3 + TypeScript + Vite

| 项 | 内容 |
|---|---|
| **决策** | 使用 Vue3 + TypeScript + Vite 构建前端 |
| **理由** | Vue3 组合式 API 更适合逻辑复用；TypeScript 提供类型安全，减少运行时错误；Vite 启动快、构建快、生态成熟 |
| **备选方案** | React、原生 JS |
| **否决理由** | React 学习成本略高，本项目不需要复杂状态管理；原生 JS 缺乏类型与工程化支持，不利于练习规范 |

### 3.2 后端：Java + Spring Boot

| 项 | 内容 |
|---|---|
| **决策** | 使用 Java 21 + Spring Boot 4.0.8 |
| **理由** | Java 生态成熟，企业应用广泛；Spring Boot 开箱即用，内嵌 Tomcat，适合快速搭建 REST API；Java 21 是当前 LTS。Spring Boot 选用 4.0.8 而非最新的 4.1.x，原因是 MyBatis 官方 starter 尚未适配 4.1.x，待适配后升级 |
| **备选方案** | Node.js + Express、Python + FastAPI |
| **否决理由** | 前后端同语言虽方便，但本项目目标是练习"前后端分离 + 企业级 Java 后端"的典型组合；FastAPI 生态与 Java 企业栈差异较大 |

### 3.3 数据库：MySQL

| 项 | 内容 |
|---|---|
| **决策** | 使用 MySQL 8.0 |
| **理由** | 关系型数据库，成熟稳定；企业使用广泛；数据结构（玩家、分数）天然适合关系模型 |
| **备选方案** | PostgreSQL、SQLite、MongoDB |
| **否决理由** | SQLite 不适合多用户并发；MongoDB 对结构化分数数据属过度设计；PostgreSQL 也优秀，但 MySQL 更常见于国内企业环境，学习价值更高 |

### 3.4 构建工具：Maven

| 项 | 内容 |
|---|---|
| **决策** | 后端使用 Maven 构建 |
| **理由** | Java 生态事实标准，配置直观，插件丰富；团队协作时约定统一 |
| **备选方案** | Gradle |
| **否决理由** | Gradle 更灵活但学习成本略高；本项目不需要复杂构建定制，Maven 足够且更普及 |

### 3.5 版本控制：Git + GitHub

| 项 | 内容 |
|---|---|
| **决策** | Git + GitHub，遵循 Conventional Commits 与分支规范 |
| **理由** | 业界标准；GitHub 提供 PR、Issue、Actions 等完整协作能力 |
| **备选方案** | GitLab、Gitee |
| **否决理由** | GitHub 生态最完整，CI/CD 支持好，学习价值高 |

## 4. 前后端职责划分

| 功能 | 前端 | 后端 |
|---|---|---|
| 蛇的移动、吃食物 | ✅ 全部逻辑 | — |
| 游戏结束判定 | ✅ 本地判定 | — |
| 计分 | ✅ 本地计分 | — |
| 上传分数 | 发起请求 | 校验 + 存储 |
| 查询最高分 | 发起请求 | 查询 + 返回 |
| 排行榜 | 渲染列表 | 查询 + 排序 + 返回 |

**原则：** 游戏逻辑放前端（实时性要求高、无需服务端参与）；数据持久化放后端（需要存储和共享）。

## 5. 数据流

以"游戏结束 → 上传分数 → 刷新排行榜"为例：

```text
1. 玩家游戏结束
       │
       ▼
2. 前端拿到本局得分
       │
       ▼
3. POST /api/scores  { playerName, score }
       │
       ▼
4. 后端校验 → 写入 MySQL
       │
       ▼
5. 返回 200 OK
       │
       ▼
6. 前端 GET /api/scores/top?limit=10
       │
       ▼
7. 后端查询 → 返回 JSON
       │
       ▼
8. 前端渲染排行榜
```

## 6. 部署架构（初步）

**开发阶段：**

- 前端：`npm run dev`，本地 Vite 服务器（默认 5173）
- 后端：`mvn spring-boot:run`，本地内嵌 Tomcat（默认 8080）
- 数据库：本地 MySQL 8.0

**生产阶段（后续）：**

- 前端：构建为静态资源，部署到 Nginx 或静态托管
- 后端：打包为 JAR，部署到服务器（Docker 容器）
- 数据库：独立 MySQL 实例

> 部署细节待 M5 之后再定，当前阶段不引入 Docker。
